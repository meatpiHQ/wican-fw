# WiCAN PRO 6.0.0-beta.14

Supported device: [WiCAN PRO](https://www.crowdsupply.com/meatpi-electronics/wican-pro) only. Home Assistant: v6 requires the ha-wican integration [2.0.0-beta1](https://github.com/jay-oswald/ha-wican/releases/tag/v2.0.0-beta1) or later.

## Before you update

<!-- /release.py:layout -->
- **Coming from 6.0.0-beta.1 to beta.9: do not let the car wake WiCAN for this update.** Those versions can destroy the OBD chip at the moment WiCAN wakes from sleep (fixed from beta.10 on; the risk is highest with the Audi Q4 e-tron, Skoda Enyaq and Elroq, VW ID and Porsche Taycan profiles). WiCAN has to be awake to be updated, so have it awake another way. Either update right after a drive, while it is still awake. Or, if it is asleep, leave the car off, unplug WiCAN, wait ten seconds, plug it back in and start the update at once. We ran both ways three times each on the bench with the chip in the state in which a wake on those versions destroys it, and the chip came through every time. If the OBD chip card says "chip not up" right after the update, the chip was damaged before it: the update does not do that, and no firmware can bring such a chip back.

## New since beta.12
- **J2534: ISO 15765 extended addressing, for an ECU behind a gateway (`ISO15765_ADDR_TYPE`).** Some cars answer diagnostics for several ECUs on one pair of CAN ids and tell them apart by one more byte in front of every frame, ISO 15765-2's extended addressing. The case this came from is Toyota and Lexus from 2019 on, where a gateway answers on 0x758 for the ECUs behind it. WiCAN refused a message with that flag (`ERR_INVALID_MSG`), so Techstream and other J2534 tools could not reach an engine ECU behind such a gateway. It now sends and receives these messages, in one frame or in many, with the flow control the tool sets, and for several ECUs behind the same two ids at once. A tool sets it up the standard way: a flow control filter with `ISO15765_ADDR_TYPE` whose pattern and flow control message carry five bytes, the id and the address byte of that direction; messages are the id, the address byte, then the data. The Windows driver needs no update (1.10.0 passes the flag through). Tested on the bench against a gateway played by a CAN adapter, with every frame read off the bus (4095 bytes each way, two ECUs answering at the same time), and by the contributor with Techstream on an engine ECU on a bench; not yet run on a car behind a real gateway.
- **J2534: one ISO 15765 channel serves ten ECUs.** A tool that opens an engine ECU sets a flow control filter for each of the response ids 7E8 to 7EF on one channel. The fifth was refused (`ERR_EXCEEDED_LIMIT`) and the tool stopped there. A channel now holds ten ECUs, the device twelve over all channels.
- **The web page says what J2534 over the USB cable needs.** A J2534 tool can reach WiCAN over the USB cable as a COM port, but only after two settings on the USB page: "Connector role" set to Device and "USB device class" set to CDC serial. As shipped the connector is in the Host role (for a modem or a GPS receiver), and a PC then shows only the board's two console ports, which do not answer J2534. Nothing on the J2534 page said so. It now has a small info button in its header that names the two settings, the role's choice and help no longer speak of a network adapter alone, and the device class has a help text.
- **Send a raw frame on any bus of the OBD connector (`can.send`, issue #1072).** Some things a car does only when it is told with a frame that is no diagnostic request: a wake-up and a remote start on a GM car's single-wire bus (where the request came from), a command to a body module on MS CAN. Until now the only way to put such a frame on single-wire, MS or CH CAN was the route behind the Test button, which is a test tool. There is now a supported way, in three forms: `POST /api/can/send` for Home Assistant or a program on a PC, the action "Send a CAN frame" on the Rules page, and `can_send()` in a script. You name the bus (`obd` for the car's own OBD bus, `ms`, `sw` or `ch` for MS, single-wire and CH CAN, `can` for WiCAN's own CAN controller), the id (11 or 29 bit) and the data. A request can carry up to eight frames with the time between them, so a sequence keeps its timing. On single-wire CAN a frame can be sent as a high-voltage wake-up (`wake`), which is what wakes a sleeping GM car. On a car older than CAN (SAE J1850, ISO 9141-2, ISO 14230) `obd` sends the message's three header bytes and its data on that protocol. Nothing of it is written to the OBD chip's memory, the answer says for every frame whether somebody on the bus acknowledged it, and the polling goes on behind it. A send through the OBD chip takes about half a second and waits while an app (a terminal, an ELM327 app) has the chip. Tested on the bench on every bus against a simulator that records each frame it reads, the wake-up against a sleeping single-wire transceiver, and on simulated J1850 VPW and ISO 9141-2 cars; not yet run on a car by us.
- **The OBD chip's firmware update asks for a fresh start first (issue #1075).** When the chip inside WiCAN needs a newer firmware (V2.3.24 in place of V2.3.22), the page no longer offers the update right away. It shows three steps instead: unplug WiCAN from the car, wait one minute, plug it back in. The update is offered when the page opens after that. The chip is then fresh from power-on with nothing in progress on it, which is the calmest moment to write it. WiCAN checks this itself, so an older copy of the page in the browser cannot start the update at another time. While the update runs (about 20 seconds) WiCAN keeps everything else away from the chip: AutoPID pauses and continues by itself afterwards, apps and the test tools get no access, and the chip is restarted cleanly before and after the write. For a script or the console, `POST /api/obd_chip/update` answers 409 with `"power_cycle": true` in any other start, and `"any_start": true` (`obd_chip update --any-start`) lifts the rule.

## Bug fixes since beta.12
- **A power cut in the first minutes after a firmware update brought the old firmware back (issue #1075).** On a WiCAN whose bootloader can fall back (units flashed over USB with version 6, and new units), a new firmware counted as unconfirmed for its first ten minutes, or until the first sleep or restart. Unplugging WiCAN in that time started the previous firmware again. After an update from beta.5 or older that is the worst outcome, because those versions rewrite the OBD chip's firmware at their first start and reset the chip in a way that could damage it. A new firmware is now confirmed at its first start, before WiCAN says a word to the OBD chip. A firmware that cannot start at all still falls back, and an update from the release list that crashes three times in a row is still rolled back.
- **WiCAN could go to sleep in the middle of a firmware upload.** With the car off, the sleep countdown kept running while a firmware file was being uploaded. When it ran out, WiCAN went to sleep, the upload was lost, and WiCAN woke later on the old firmware. WiCAN now stays awake while a firmware image is being received, from an upload or from the release list, until it has restarted into it. The countdown bar says "Kept awake while the firmware is updated".
- **The OBD chip update sometimes did not start while AutoPID was polling.** With a vehicle profile polled at a short period, the update could not get hold of the chip and the page said "the update did not start". Nothing was written and the chip was fine, but the update had to be tried again. AutoPID now steps aside as soon as the update is asked for.
- **The CAN self-test could report a hardware fault on a healthy WiCAN while AutoPID was polling.** The self-test (System > Maintenance) lets the OBD chip ask for engine speed and WiCAN's own CAN controller answer it. With AutoPID polling a vehicle profile, the chip could still carry the receive filter of the row polled last, and it then ignored the answer to the test's request. The test said "the ESP32 answered but the chip never printed it: the ESP32's transmit path or its standby pin", or it was refused with "the OBD chip could not be claimed". On our bench that happened in 12 of 24 runs. The test now pauses AutoPID for its two seconds, puts the chip back to its defaults before it asks, and AutoPID carries on by itself afterwards. When AutoPID is polling, the page tells you so before the test starts.
- **A restart could interrupt the OBD chip's firmware update.** A restart asked for while the chip was being written (the Reboot button in another tab, a settings change that restarts) went ahead in the middle of the write, and the next start had to finish it. The Reboot button now answers "not now: the OBD chip's firmware is being updated", and a restart that WiCAN plans itself waits until the chip is up again.
- **Reading the chip while AutoPID polled a large table failed now and then.** "Read the chip configuration" on the OBD chip card could answer "Could not read the chip", and the console's `obd_chip` printed no version, because AutoPID left no pause in which another reader could get the chip. AutoPID now steps back for a moment whenever something else is waiting for the chip.
- **The OBD chip card said "last update: ESP_ERR_TIMEOUT" for a chip that did not answer (issue #1075).** That read as a failed chip update. Nothing had been written: WiCAN asks the chip for its version at every start, and a chip that is not up gives no answer. The card now says "not checked: the chip did not answer".
- **J2534: messages written together lost their transmit confirmations.** When a tool wrote more than three ISO 15765 messages in one `PassThruWriteMsgs`, only the last three got their TxDone indication, and with driver 1.10.0 the next read came back `ERR_BUFFER_OVERFLOW`, which Toyota's Calibration Update Wizard takes as fatal at its login to the ECU. Every message of a write gets its confirmation now.
- **J2534: an ECU's short reply was read after the start of the long reply that followed it.** When an ECU acknowledged a request with one frame and at once began a longer answer on the same id, the tool read the START_OF_MESSAGE indication of the second message before the first message. They are read in the order they were on the bus.

## Known issues
- A few published vehicle profiles carry rows that never read right on any firmware version (an i3 and Mini state of charge, the bZ4X cell list, a Volvo XC40 state of charge, the pack voltage ranges of the 800 V Hyundai, Kia, Genesis and Xpeng cars). They are being corrected on the profile side.
- A TP 2.0 (VW) reflash by a tool that does the transport itself on a raw CAN channel runs at one round trip per block acknowledgement (about 3 ms over USB, 28 ms over WiFi): flash over the USB cable, or use the TP 2.0 protocol (`TP2_0_PS`).
- The ESPNetLink cannot update itself yet; it updates through a WiCAN PRO. A dongle on firmware 1.20 or older must be flashed once over USB.
- J2534: J1850 PWM and K-line are not supported; J1850 VPW is request and response only, no 4x speed.
- A firmware upload started within ten minutes of an update may show that update as "not yet verified" on the Updates card until the ten-minute mark.
