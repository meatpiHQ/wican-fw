# WiCAN PRO 6.0.0-beta.11

Supported device: [WiCAN PRO](https://www.crowdsupply.com/meatpi-electronics/wican-pro) only. Home Assistant: v6 requires the [meatpi-multi-device](https://github.com/meatpiHQ/ha-wican/tree/meatpi-multi-device) branch of the ha-wican integration.

## New since beta.10
- **Windows J2534 driver 1.7.0.** The installer in [drivers/j2534](https://github.com/meatpiHQ/wican-fw/tree/dev-v6/drivers/j2534) is updated. A PassThru tool that asks for the battery voltage (`READ_VBATT`) now gets the voltage WiCAN measures, in millivolts; driver 1.6 answered 12.0 V by itself and never asked the device. This needs WiCAN firmware 6.0.0-beta.10 or later: against older firmware the driver reports that the firmware has to be updated instead of inventing a value. The driver is now free software under the GNU General Public License, version 3, with its source at [wican-j2534-driver](https://github.com/meatpiHQ/wican-j2534-driver), and its installer opens with a disclaimer that has to be accepted before anything is installed: the driver passes on whatever the tool sends to the car, ECU reprogramming included, and is used at your own risk. The disclaimer and the licence are installed next to the driver. The page the installer ends on no longer says that reflashing is blocked until a switch is turned on: that switch went with the firmware of 2026-10-27, and the WiCAN forwards everything a tool sends once the J2534 server is enabled.
- **CAN filters can be added and edited in the web UI.** A CAN filter reads a frame the car sends by itself, without asking for it: a CAN ID, how long to listen for it, and one or more values decoded from the frame's data bytes. Until now a filter could only arrive with a vehicle profile, from a DBC file or through the Raw Config tab. On the Automate page, under Parameters, the Vehicle Specific tab and the Custom PIDs tab now each have a CAN filters list under their PIDs: Add CAN filter adds one, every field of a filter can be edited (the filters a vehicle profile brought too, and more can be added beside them), a filter can be switched off or removed, and its live value shows in the list. The filters on Vehicle Specific belong to the vehicle: choosing another profile replaces them, as it replaces the vehicle-specific PIDs. The filters on Custom PIDs stay. The CAN ID is typed as in the 4.x firmware: `0x284` in hex or `644` in decimal, and the field then shows it in hex. The box above the lists now says Search (it said Filter) and searches the PIDs and the filters. As before, nothing reaches the device until Apply Configuration.
- **Test for a CAN filter.** Each filter has a Test button, like a PID: WiCAN listens once for the frame and shows what it sent to the OBD chip, the frame it received, its data bytes as the expressions count them (B0 is the first data byte) and every decoded value, or says that no frame with that CAN ID came in the listen time. The car has to be on and sending the frame.
- **The switch of a tab now covers its CAN filters.** With Poll vehicle-specific PIDs off the vehicle's CAN filters rest, with Poll custom PIDs off the custom ones. Before this version a CAN filter went on whatever these two switches said. If you had switched one of them off and count on a CAN filter being read, switch it on again and switch off the PIDs you do not want one by one.

## Bug fixes since beta.10
- **The Logger stopped recording on a WiCAN that was short of internal memory, on a good SD card.** The Logger page then showed no file name while Dropped kept rising, System Monitor listed the fault `logger_storage_error` with the detail `params`, the newest log file could not be downloaded (`file in use`), and only a restart brought logging back, until the next time. Three things came together. The Logger gave its 4 KB write buffer back every time it closed its file (at every new file, and every time the web page read the file that is being written) and could not get it again once internal memory had no block of that size left. When memory was so low that a write to the card failed, closing the file left it locked until the next restart, for the Logger and for a download alike. And with next to no memory left, opening a file restarted the device (`abort() ... task "dl_writer"` in the crash report). The Logger now takes its buffer once, when it starts, and keeps it; a file whose close fails is released; and the Logger no longer opens a file when there is no memory for it: it waits, keeps what it can in its queue, and goes on by itself when memory is back. If it had to wait, the fault's detail reads `params: out of internal RAM`, so that nobody looks for the cause on the card. Reported on 6.0.0-beta.5. On that version Bluetooth together with a VPN leaves about 5 KB of internal memory (measured on the bench, and the reading in the report); the same settings leave about 58 KB on this version.
- **A good log file could be set aside as corrupt, or deleted, when internal memory ran out.** With no memory for the SD card driver a read from the card came back empty, the SQLite format took that for a damaged file, and the Logger set the file aside (`.corrupt`) or, when even the rename failed, deleted it to go on. While WiCAN cannot read its card for want of memory the Logger now leaves the file alone and tries again later.
- **A download from the SD card returned an empty file and left the file locked when internal memory was low.** Since 6.0.0-beta.6 a download read the card through a helper task that is created when needed and needs 4 KB of internal memory; when there was none, the download answered with nothing and never closed the file, which stayed locked until the restart. If it was the log file being written, the Logger could not continue (`logger_storage_error`). Downloads from the card no longer need that task.
- **Low internal memory was never reported.** The fault `internal_ram_low` (free internal memory under 8 KB, or its lowest point since the start under 4 KB, with the numbers in its detail) exists since the first v6 betas, but the check behind it was never started, so System Monitor never showed it. It is started now. If you see it, the features in use need more internal memory than this WiCAN has: switch off one you do not need (Bluetooth and a VPN are the largest), and send the detail with a report.
- **A CAN filter read only part of some frames.** WiCAN listened for a filter's frame with the OBD chip treating every frame as a diagnostic message, in which the first byte is a length. A frame whose first data byte was 01 to 07 was therefore cut to that many bytes, and a value further back in the frame stayed empty for as long as that byte had such a value (a counter or a gear, for example), while the same frame was read whole when the byte had another value. The frame is now read whole whatever it starts with. Found on the bench while testing the new CAN filters list; it affected filters from a vehicle profile and from a DBC file in every earlier v6 beta. The 4.x firmware read such frames whole.
- **A CAN filter with a 29-bit ID read nothing on a car that uses 11-bit IDs, and the other way round.** WiCAN listened for a filter's frame on whatever protocol the OBD chip was on at that moment, and the chip only lets through IDs of that protocol's length. A filter with a 29-bit ID (above 0x7FF) therefore never saw its frame on a car whose diagnostic protocol uses 11-bit IDs. And with a vehicle profile whose PIDs switch between the two kinds of protocol themselves, a filter stopped updating behind a PID of the other kind. WiCAN now puts the chip on the 11-bit or the 29-bit protocol of the same speed for the moment it listens and back afterwards, as the 4.x firmware did.
