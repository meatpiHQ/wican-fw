# J2534 ISO 15765 extended addressing (ISO15765_ADDR_TYPE)

Command: `.\test.ps1 j2534ext` = `python tools\testbench\usb\j2534_ext_addr_bench.py --dut localhost:18081 --j2534 localhost:18534 --pcan <the PCAN channel on the DUT's bus> [--dll <built wican_j2534.dll>]` (PC; two ssh forwards through rpi001: 18081 to the DUT's port 80, 18534 to its J2534 port 6809)

Needs: a firmware that takes `ISO15765_ADDR_TYPE` on the DUT (components from 2026-11-20) + rpi001 + PCAN on the DUT's bus (`WICAN_PCAN_DUT`: listen on both channels first, the adapter's plugs have been swapped before) + for leg D the 32-bit Python and a built driver DLL (the stage passes `WICAN_J2534_DLL` when set, else `..\..\wican-j2534-driver\build\Release\wican_j2534.dll` when that file exists, and skips the leg with a note when there is none; any driver from 1.10 does, the DLL passes the flag and the fifth byte through).

A standard tool's byte stream in normal addressing: [j2534std.md](j2534std.md). ## What it covers

ISO 15765-2 knows a second way to address an ECU: one byte, the address extension, in front of every frame of a message. A gateway that answers for the ECUs behind it uses it, so one pair of CAN ids carries several conversations and every frame holds one byte less (a single frame 6, a first frame 5, a consecutive frame 6). SAE J2534-1 names it `ISO15765_ADDR_TYPE`: a message is `[4-byte id][address extension][payload]` both ways, and a FLOW_CONTROL filter's pattern and flow-control message carry the id and the address extension of their direction. Until 2026-11-19 the device answered a message with that flag `ERR_INVALID_MSG`. meatpi-components pull request 5 (bachajon) added it for Toyota's gateway (requests on 0x750, answers on 0x758), in the vendored ISO-TP link, the provider and the J2534 channel; its transmit side ran on the contributor's bench with Techstream, its receive side had never run on hardware. This stage is that run, with our changes on top (the layout as pure code, the receive side in a file of its own, a filter of the other kind on the same ids).

The bench plays the gateway on the PCAN the way ISO 15765-2 writes it: requests on 0x6F5, answers on 0x6FD (ids the bench simulator does not answer), two ECUs behind it. The tester's frames to the first are led by 41 and its answers by E9, the second 42 and 5F: the byte differs by direction, so a device that mixes up the two fails. A third ECU speaks normal addressing on 0x6F6 / 0x6FE. Every frame the device sends is read off the bus and compared whole. An ECU answers `22 hh ll ss` with 0xhhll bytes (`62 hh ll ss`, then a pattern seeded by ss), `31 01 hh ll ss` with the single frame `71 01` and at once a message of 0xhhll bytes, anything else with its bytes back (the first one + 0x40). The tester is the wire client of the other J2534 stages at wire version 2, so a loss would be told.

## What it does not cover

- A real gateway and a real tool. The gateway here is a model of ISO 15765-2, and its two address extensions are the bench's. The contributor ran Techstream and Toyota's Calibration Update Wizard against a 2GR-FKS engine ECU on a bench without a gateway (the transmit side); a car with the gateway in front is the field case.
- 29-bit ids with an address extension (the code path is the same, the id width is one flag), a bus at another speed than 500 kbit/s, the USB and BLE transports (the runs went over WiFi through the tunnel).
- Mixed addressing by its ISO name (29-bit ids with an address extension as ISO 15765-2 annex lays the ids out): the device does not interpret the ids.
- An answer in extended addressing without a FLOW_CONTROL filter: the PASS path reads normal addressing, by design (the wire protocol's section 3).
- A segmented message that the device RECEIVES while it sends one to the same ECU.
- Leg F is 3000 frames a second, not the line rate: the Python sender is paced so that the adapter's transmit queue does not hold the ECUs' frames back. The line rate on an ISO15765 channel is [j2534fc.md](j2534fc.md)'s legs N and W.

## Traps

- `WICAN_PCAN_DUT` must name the PCAN channel on the DUT's bus in the same PowerShell command. On the wrong channel no ECU hears a request and every check from S on fails; a 500 kbit/s frame on the other (125 kbit/s) bus also draws error frames there.
- The stage fails from A1 on against a firmware before the change (`ERR_INVALID_MSG` for the flag): that is what it is for. `--before` is the run for such a firmware.
- Leg T holds the gateway's answers until both requests are in (`bus.hold`). Without it the first ECU has often finished before the second request is written and the two answers do not overlap: the leg would pass without testing anything, which is why T1 also asks for at least 40 changes of sender.
- Leg L counts the provider's sessions absolutely (twelve): it wants no UDS request of the device's own in the 5 s before it (the UDS client holds a session that long) and no other J2534 channel left open.
- The internal RAM figure of leg L is the difference of two readings of `/api/status` around ten opens, with web requests in between: a session's own share is 288 B on the run of the first record, and the leg only asserts it is under 2 KB.
- The ECU model sends a frame with a busy wait for the gap, so the gaps it leaves are at least what a flow control asks; the bench does not measure the device against the gap.
