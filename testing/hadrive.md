# A drive, recorded and backfilled: the simulator, the SD card log, Home Assistant

Command: `.\test.ps1 hadrive -DeviceId <id> [-DriveArgs '<the bench's arguments>']` (= `python tools/testbench/ha/ha_drive_backfill_bench.py --dut localhost:18089 --dut-ip <DutIp> --pi rpi001 <arguments>` through an ssh tunnel to the DUT via rpi001; by hand through your own tunnel the same way). The comparison alone over a finished run's folder: `python tools/testbench/ha/drive_report.py <logdir>` (or the bench with `--report-only <logdir>`).

Needs: the P4 bench AP on rpi001 with its lever daemon (`ap off` / `ap on`; the bench starts the daemon when it is down, `--away push` works without it), the DUT on that AP with an SD card, ECU sim v2 on the bus and on the PC's USB link, a Home Assistant on rpi001 (`--ha-install fresh`, the default: the current release with the integration's public release, started when it is down and stopped at the end; `bench` = the 2026-09 install), its owner login (on the Pi for `fresh`, `internal/bench_ha_credentials.json` for `bench`, or `--ha-user` / `--ha-pass`).

Index row and the other stages: [../TESTING.md](../TESTING.md). The seeded-series bench for the same feature: [habackfill.md](habackfill.md).

**What it covers.** The users' report of 2026-11-21: after a drive away from the home WiFi the history in Home Assistant has holes, some parameters come back and others do not. `habackfill` proves the import with a series written into the past in seconds; this bench plays the drive itself in real time and keeps three records side by side, so the place where a value is lost can be named:

1. **the truth**: every value the bench sets in ECU sim v2 (`POST /api/ecu/pids/<mode>/<pid>`), stamped before and after the request (`truth.jsonl`);
2. **the unit's log**: what the WiCAN recorded on its SD card, read back through `GET /api/logger/export` once the drive is over (`device_rows.jsonl`);
3. **Home Assistant**: the hourly statistics (what the integration's import writes), the five-minute statistics and the plain states the History panel draws (`ha_stats_hour.json`, `ha_stats_5min.json`, `ha_states.json`).

The run folder (`test-reports/logs/hadrive_<stamp>/`) also keeps `run.json` (the plan, the phases, the clocks, the entities, every catch-up run the integration made), `monitor.jsonl` (the unit's logger, webhook and sleep figures every 10 s while it can be reached) and the reports: `report.md`, `report.json`, `report.html` (the verdict, a table per parameter and a chart per parameter with the three records over time, the away time shaded, a tooltip under the cursor).

A file named `STOP` in the run folder ends the drive early; the return, the settle and the comparison run as usual.

**The drive profile** (`tools/testbench/ha/fixtures/drive_default.json`, patterns in `drive_sim.py`): 14 standard PIDs of the simulator with every kind of signal on purpose: fast ones (engine speed as a sine, vehicle speed as a stop-and-go course, load as random steps, throttle and system voltage as walks), slow ones (intake air temperature, barometric pressure in 10 min steps, the fuel level falling one percent every five minutes), one that stops changing after the warm-up (coolant), one that never changes (ambient air temperature) and a counter whose value is the time itself (a missing period shows as a jump). A parameter names its place in the simulator (`sim`: `<mode>/<pid>/<param>`), the AutoPID row that reads it (`row`), its pattern, the grid a value is rounded to (`step`) and how far the logged value may be from the set one (`tol`, the OBD byte's resolution). `python tools/testbench/ha/drive_sim.py --profile <file> --preview 600` prints a profile's values without a simulator. Parameters of the unit's table that the profile does not drive (a car profile's rows) stay at what the simulator holds and are compared too (the log's continuity and Home Assistant's hours).

**What is held (the verdict).**

- `[log]` every parameter is recorded through the away time (the share of the samples the table's period gives, no hole longer than the limit); every recorded value of a driven parameter is one the simulator held at that moment (within the slack and the tolerance); every value the simulator held long enough shows in the log; from the logger's start to the drive every row carries the value the simulator held as the run found it (judged when the run switched the logger on itself; one wrong row fails it, nothing was moving yet); the logger dropped no row.
- `[ha]` every recorded parameter has a sensor; for every hour that had ended when the run looked, Home Assistant's statistics row equals the mean, minimum and maximum of the unit's rows of that hour **in the unit Home Assistant keeps the sensor in** (exact / differs / missing; an hour still running is `pending` and proves nothing). The judge converts the unit's value first (°C to °F, km/h to mph, km to mi, kPa to hPa, psi or inHg; `unit_converter` in `drive_report.py`, Home Assistant's own constants): an hour that went in as the logged number reads `differs`, with both numbers and both units in the detail, and a note lists the sensors that hold such hours.
- `[ha]` a sensor's live states are the values the unit logged at that moment, in the unit Home Assistant shows (a state against the rows of the 30 s before it, to half of the state's last digit): this also proves the judge's own conversion table against Home Assistant's.
- `[ha]` with an integration that fills History (2.0.0-beta2 on; the run sees it in the integration's diagnostics): every parameter whose value changed while away has states from the away time, and each of those states is a value the unit logged within 2.5 s of the state's own stamp. With an older integration this is a note (0 states from the away time).
- `[ha]` with a park across the top of the hour and an integration that keeps the pulled rows: the hour of the return was in the statistics while the unit slept. The monitor reads the hourly statistics at the moment the integration reports `hours_from_kept_copy` (`ha_stats_hour_kept.json`), and the judge holds each sensor's row of that hour against the unit's rows up to the pull at the return (the pull reads what the unit had written to its card by then: the rows of its last 20 s may or may not be in it).
- The unit's own battery voltage (`device.batt_voltage` in the log since firmware 6.0.0-beta.15) is judged like a parameter, against the device's Battery Voltage sensor: its rows through the away time, its hours, its states.
- `[d4]` Home Assistant's own hourly statistics are whole. The bench keeps a sensor of its own moving in Home Assistant (`sensor.hadrive_control`, a state every 20 s, removed at the end); its hourly statistics are Home Assistant's work alone. It must have a row for every hour of the run that is over, and Home Assistant's log must hold no `Blocked attempt to insert duplicated statistic rows`. Home Assistant writes the rows of an hour for all sensors in one go, ten seconds past the hour, and gives the whole write up when one of the rows is there already: an import that came first costs every other sensor that hour.
- `[d4]` the export route reads its query values as a browser or a script library writes them (firmware 6.0.0-beta.15 on): the page after a cursor whose colon is written `%3A` is the page after the raw cursor (and not the first page again), and a parameter name with every character written `%XX` selects the same rows as the raw name.
- per trip: the home network gone, the unit back, a push after the return, the integration's pull after the return and without an error; the follow-up past the hour ran by itself (`--settle followup`).
- restore: the simulator's values, the AutoPID table, the settings (one planned restart), the webhook registration, the run's log files, the entry the run added and the Home Assistant it started, all as found; no unexpected reset, no E line from the logger, the pushes, AutoPID or the sleep manager.

Notes, not verdicts: how many states Home Assistant has from the away time, which sensors Home Assistant keeps in another unit than the unit logs, and how many parameter-hours were still pending.

**Traps.**

- The integration imports nothing from the hour still running: a drive that ends at 15:06 has its 15:00 hour imported by the follow-up at 16:01:30, and only when the unit can still be reached then. A run with `--settle none` right after a short drive compares no finished hour and says so (`nothing proven`).
- The bench AP's lever daemon is not started at the Pi's boot. Starting it restarts the AP, which then has an empty station table while the unit keeps its old association: the bench switches the AP off and on once after starting the daemon, and the unit joins within seconds.
- The unit's rows are stamped by its own clock, the truth by the PC's, the statistics by Home Assistant's: the bench measures both offsets at the start and at the end and moves every time onto the unit's clock. A PC clock that jumps during a run moves the truth.
- A Home Assistant access token lives 30 minutes: the bench signs in again when a request is refused.
- The export route gives about 64 KB a page: an hour of 30 parameters at 1 s is about 108,000 rows and about 100 pages for the bench's own read at the end. The integration reads at most 200 pages or 200,000 rows a run and comes back a minute later for the rest.
- `--leave-at-minute` waits for the NEXT time the clock shows that minute: a value just passed means almost an hour at home.
- (Until firmware 6.0.0-beta.14; the route decodes its query values since.) The export cursor (`<file-epoch>:<offset>`) goes back to the unit as it came, its colon NOT percent-encoded: the route does not decode `%3A`, reads such a cursor as a plain epoch and serves the file's first page again with `more` true and the same cursor (the bench's first run read page 1 twice and stopped, which looked like a 100 s hole at the end of every parameter). The integration sends the colon as it is.
- A unit whose table carries a car profile's rows (the bench unit: 16 standard rows and 13 of the Audi MEB profile, each with its own header and protocol words) needs about 7.8 s for one lap of a 1000 ms group: every parameter gets a row every 7.8 s, about 13,800 rows an hour, not the 108,000 the period suggests. The judge takes a parameter's period from its own rows (the median step), so the coverage and the hole limit follow the unit.
- A run of hours must not be a background task of a shell that ends tasks after ten minutes: start it detached (`Start-Process` with the output redirected, or `.\test.ps1 hadrive` in a terminal of its own). A run that is killed has restored nothing: the logger stays on, the entry stays in Home Assistant, and the next run takes that state for "as found".
- Home Assistant keeps a sensor in a unit of its own choice, fixed when the sensor is created: on a metric system the barometric pressure in hPa (the unit logs kPa), on a US system the temperatures in °F, the speed in mph, the distances in mi, the pressures in psi and inHg (12 of the bench unit's 30 sensors). `--ha-units us_customary` switches the system before the run adds its entry; an entry that is there already keeps its sensors' units.
- Home Assistant also keeps a statistic's unit when its sensor's unit changes later, and converts the new states into the old unit: an earlier run's hours in °C make a US run's statistics °C as well, and the import's numbers fit by accident. `--clear-stats` deletes the sensors' statistics before the drive; a run that switched the unit system deletes them again at its end, or the next metric run would meet statistics in °F.
- With the integration's public release (2.0.0-beta1) the History panel never shows what the import wrote: it draws states, and that import writes long-term statistics only. A statistics graph card with the period set to an hour shows them. From 2.0.0-beta2 on the integration writes the away time's values as states too.
- `test.ps1`'s preflight looks at the serial ports: do not run another stage (not even `host`) while a drive runs.
- A reproduce loop or a run that ended before it read the log knows no file name: clean up by the card's list (`GET /api/fs/list?path=/sd/logs`), or the next run finds a log file "as found" and leaves it.
- What the History panel shows for a window: `node tools/testbench/ha/ha_history_shot.mjs <ha url> <user> <password> <out.png> <start ISO> <end ISO> <entity,entity>` (run with `--keep-ha`, which leaves Home Assistant up and the entry in place).
