# J2534 TP2.0 (TP2_0_PS) against an ECU that follows SAE J2819

Command: `.\test.ps1 j2534tp20` = `python tools\testbench\usb\j2534_tp20_ps_bench.py --dut localhost:18081 --j2534 localhost:18534 --pcan <the PCAN channel on the DUT's bus> [--dll <built wican_j2534.dll>]` (PC; two ssh forwards through rpi001: 18081 to the DUT's port 80, 18534 to its J2534 port 6809)

Needs: a firmware that serves TP2_0_PS on the DUT + rpi001 + PCAN on the DUT's bus (`WICAN_PCAN_DUT`, the adapter's plugs may be swapped) + for leg L the 32-bit Python and a built driver DLL (the stage passes `..\..\wican-j2534-driver\build\Release\wican_j2534.dll` when that file exists, and skips the leg with a note when it does not). Prints `J2534 TP20 PASS`. About 1 min: two planned restarts of the unit when its J2534 server is off as found.

The index row and the other stages: [../TESTING.md](../TESTING.md). The raw CAN side of TP 2.0 (a tool that does the transport itself): [j2534_tp20_responder.md](j2534_tp20_responder.md), [j2534_tp20_gate_bench.md](j2534_tp20_gate_bench.md).

## What it covers

TP2.0 is its own J2534 protocol here (SAE J2534-2 section 19, protocol id 0x800E): the device sets the channel up, segments and reassembles messages, acknowledges blocks and keeps the connection alive, and the application sees whole messages and two indications. The bench plays the other end of the bus the way SAE J2819 writes it down: ECUs on the PCAN (identifier 0x200 + address; the first is 0x201 and receives on 0x740 as a real engine ECU does; block size 15), which answer a channel setup, the connection setup and every connection test, acknowledge data, answer a few request kinds, can lose a telegram, say "not ready" or send a break on purpose, and record everything they see, the broadcast telegrams included. The device is driven over the wire protocol the Windows DLL speaks, with the indications kept; leg L then calls the DLL itself.

The model is written from the document, so agreement with it proves agreement with the document. Two things stand outside that circle: leg J replays an exchange published from a real car ([jazdw.net/tp20](https://jazdw.net/tp20)) and compares both sides byte for byte, and the same page (taken from real VW traffic) says what the model does about the connection test (answered with the parameters response), the disconnect (answered with a disconnect), the acknowledge numbering and the two length bytes.

| I | GET_DEVICE_INFO with a parameter list (SAE J2534-2 section 25): TP2_0_SUPPORTED and TP2_0_SIMULTANEOUS 0x00000100, TP2_0_PS_J1962 answered in "supported" for the pin bitmap asked (pins 6 and 14 yes, pins 1 and 2 no, the value left alone), an unknown parameter not supported with NOERROR |
| K | REQUEST_CONNECTION: the setup on 0x200 as `01 C0 00 10 00 03 01`, CONNECTION_ESTABLISHED with the RX id then the TX id, the connection setup `A0` with a block size of 1 to 15 and FF in the unused time bytes |
| J | the published exchange of a real engine ECU: `10 89` answered `50 89`, `21 01` answered by 26 bytes in four telegrams; the eleven telegrams of both sides (`740 10 00 02 10 89`, `300 B1`, .. `300 14 00 25 00 00 25 00 00`, `740 B5`) are the page's, byte for byte |
| D | a short request answered by a 42-byte message (6 telegrams) read whole; a 601-byte request (86 telegrams) arrives whole, an acknowledge asked for at every block end |
| W | a message goes out as written and comes in as sent (SAE J2534-2 19.3.1: "Messages passed to PassThruWriteMsgs by the application will include all message address and data bytes"; in SAE J2819 a message ends at the end-of-message telegram and has no length field). The two length bytes a VW ECU wants in front of a message are the application's: `00 02 1A 9B` written is one telegram with those four bytes; the answer is read with the ECU's own `00 2A` in front; a message written without them goes out without them; the id alone is one empty end-of-message telegram; a message whose length bytes say more, or less, than came is handed over as it came, as one message; 4093 bytes are refused on the way out (ERR_INVALID_MSG, nothing sent) and not handed over on the way in (every block acknowledged, the connection kept) |
| T | 7.5 s without traffic: a connection test about once a second, each answered by the ECU with a connection acknowledge (J2819 5.2, 6.2.9); the connection is not reported lost, no disconnect goes out, a request after the pause is answered |
| M | four connections at once (J2819 5.2): three more ECUs come up each with its own two ids, a fifth request is refused at once with nothing sent, a request to each of the four is answered, every connection is tested about once a second, the three are torn down (CONNECTION_LOST per RX id, a disconnect per ECU), the first one is still there |
| N | the largest message at full speed, counted (`--big`, 10 each way): 4092 bytes written to an ECU that asks for no gap between telegrams (T3 = 0), then read back with none, every byte compared; the CAN node's loss counters (`rx_missed`, `rx_overrun`, `tx_lost`, `dispatch_drops`, `tx_errors`, `rx_errors`, `rx_bad`, `bus_off`) unchanged and its `tx` / `rx` up by at least the data telegrams |
| O | beside another protocol: an ISO15765 channel of the same tester talks UDS to the simulator (7E0 / 7E8) while the TP2.0 connection stays up and answers before and after |
| G | trouble, injected by the ECU (J2819 5.2, table 8, 6.2.4 to 6.2.7): a telegram lost inside a block (the ECU names it at the block end, the device sends again from it), the block-end telegram lost (sent again after T1), receiver not ready (the device waits T_WAIT, measured, and goes on with no telegram twice), not ready with a telegram to send again, a telegram of the ECU's 4092-byte answer lost (the device names it in its acknowledge), a break (the device ends the message with an end-of-message telegram, the write returns ERR_FAILED, the connection is kept) |
| B | a broadcast: five telegrams 20 ms apart, the request bytes kept, the two key bytes `55 55`, `AA AA`, `55 55`, `AA AA`, `55 55` (J2819 5.1.2); the flag on a non-broadcast address is ERR_INVALID_MSG |
| R | the re-triggered broadcast (START_PERIODIC with the broadcast flag, 300 ms): the five, then ONE telegram per period, the key alternating over the whole run; nothing after STOP_PERIODIC |
| E | a 9-byte message to an id without a connection is ERR_NO_CONNECTION_ESTABLISHED 0x00010001 (SAE J2534-2 table 123); a 3-byte one goes out as one CAN frame |
| F | a request nobody answers: repeated 10 times T_E (100 ms) apart, then CONNECTION_LOST with the RX id of the request and reason 1 |
| Q | only with `--soak S`: S seconds without traffic, a test about every second all the way (none more than 1.3 s after the one before), the connection kept |
| X | TEARDOWN_CONNECTION: the ECU sees the disconnect, CONNECTION_LOST with reason 0, and the ECU saw nothing J2819 does not allow over the whole run |
| L | the driver DLL called like an application (`j2534_tp20_ps_dll_check.py`, 32-bit Python): GET_DEVICE_INFO with input NULL and an SPARAM_LIST, GET_DEVICE_INFO without a list (ERR_NULL_PARAMETER), CONNECT, SET_CONFIG with an SCONFIG_LIST, REQUEST_CONNECTION and TEARDOWN_CONNECTION with SBYTE_ARRAYs, a request and its answer, 0x00010001 from PassThruWriteMsgs with the last-error text naming it |
| Z | settings back as found, only the planned restarts, no new E lines |

## What it does not cover

- A real ECU. The ECUs here are a model of the document, checked against one published real exchange; a car is the proof (the contributor's test on a VW ECU is the next step).
- An application that expects the device to add the two length bytes. Until 2026-11-16 the contribution added them on send and took them off on receive; since then the device passes a message as written (leg W), which is what SAE J2534-2 says. The bench's ECUs expect the bytes on the wire, as real VW ECUs do (the published exchange has them), and the bench adds them the way an application has to. No application for another J2534 TP2.0 interface was found to compare with: the tools known to speak TP 2.0 do the transport themselves on a raw CAN channel.
- A second J2534 interface as a reference. A Tactrix Openport 2.0 (firmware 1.17.4877, driver 1.02.4820) put on the bench bus in the WiCAN's place on 2026-11-16 refuses `TP2_0_PS`, and every other SAE J2534-2 protocol id, with ERR_INVALID_PROTOCOL_ID (`j2534_tp20_ps_dll_check.py` with `WICAN_J2534_DLL` naming its DLL). A VW tool that runs on it therefore does TP 2.0 itself on a raw CAN channel.
- A bus that loses frames by itself, a real bus-off, the USB transports (the runs so far went over WiFi through the tunnel).
- The passive connection (an ECU asks the tester for a channel), GET_PROTOCOL_INFO, `J1962_PINS` as a precondition (the pins are preset), loopback, a break while the device is the one receiving.

## Traps

- The PCAN channel on the unit's bus comes from `WICAN_PCAN_DUT` (or `--pcan`), and a new PowerShell window does not have it. Without it the bench listens on channel 1; on a bench where the unit is on channel 2 every check that looks at the bus then fails with an empty list, from K2 on (the bench prints a line that says so).
- The bench's ECUs sit on the PCAN beside ECU sim v2. The simulator does not answer on 0x200 to 0x206, 0x300 to 0x30F or 0x740 to 0x745; if a profile ever does, this bench reads its frames as its own. Leg O needs the simulator to answer UDS on 7E0.
- The model runs in Python on Windows: it sees a telegram some milliseconds after the bus did. A fault "after telegram 20" therefore lands later on the bus (the break reached the device ten telegrams on); the checks allow for it and do not time the device against the model, only against the bus timestamps of the PCAN.
- One fault per message: an ECU's `fault` is cleared when it fires, and a case passes only when it did fire (the last element of a failed case's detail is the fault that never came).
- AutoPID is paused for the run and switched back on in leg Z; a run killed in between leaves the groups off.
- `--keep` leaves `j2534_server.enabled` and `allow_lan` on (for a second run in the same boot, for example to read task stacks): put them back by hand or with a run without it.
- A driver before 1.8 does not serve TP2_0_PS: without `--dll` leg L is skipped, it does not fail.
