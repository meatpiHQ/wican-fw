# The speed a TP 2.0 tool gets through the DLL

Command: `python tools/testbench/usb/j2534_tp20_responder.py --blocks 240 --t3-ms 1` (PC, PCAN) in one window, then `C:\Users\Ali\idf_tmp\py32\python.exe -I tools/testbench/usb/j2534_tp20_tester.py --blocks 240 --batch 1` with `WICAN_J2534_HOST=192.168.82.1` (USB-NCM), `WICAN_J2534_COM=auto` (USB CDC serial, env `-u WICAN_J2534_HOST`) or the tunnel's `127.0.0.1:18534` (WiFi), `WICAN_J2534_DLL=<path>` for a built DLL

Needs: PCAN on the DUT bus; `j2534_server.enabled` (and `can_manager.enabled`, off on a fresh unit); `usb_host_manager.role=device` with `device_class` ncm or cdc for the USB legs

Tester flags (2026-11-05): `--pass-filter` arms a pass-all PASS filter after CONNECT (a SAE J2534-1 device such as the Tactrix Openport receives NOTHING until one is set; the WiCAN passes everything without one), `--write-timeout MS` is the `PassThruWriteMsgs` Timeout (default 0 = queue and return per J2534-1; driver 1.6 honours it), `WICAN_J2534_DLL` may name any J2534 DLL. The reference device: `python tools/testbench/usb/op20_raw_tester.py --blocks 40 [--wait-ack]` (64-bit Python, ctypes over WinUSB) runs the same transfer straight into a Tactrix Openport 2.0 with the device's own ASCII protocol, for the number no DLL adds to.

**The reference, 2026-11-05 (a Tactrix Openport 2.0, firmware 1.17.4877, on the PCAN bus, T3 1 ms, BS 15, 40 blocks):** the block-end ACK latency the ECU sees is **1.3 ms** (p95 1.6, max 2.1) whether the tool waits for the device's transmit confirmation (`aro`, 0.6 ms after the write call) or not; the USB write call itself takes 0.1 ms, its DLL's `PassThruWriteMsgs` 0.5 ms with no wait for the bus. **Through the official Tactrix driver (`op20pt32.dll` of 2016-07-07, the kernel driver `openport.sys` bound, 2026-11-06, the simulator back on the bus as its termination):** ACK latency **1.4 ms** (p95 1.6, max 2.3) with `PassThruWriteMsgs` Timeout 0 (the call returns in 0.1 ms), 1.5 ms with Timeout 100 (the call then waits for the bus: 0.8 to 0.9 ms), so the official driver does what SAE J2534-1 says and what WiCAN driver 1.6 does; a tool that asks for 16 messages per `PassThruReadMsgs` with a 20 ms Timeout pays the same amplifier on the Openport as on the WiCAN: 15.7 ms per ACK (the driver waits the Timeout for the 16th message), 13.5 min projected against 8.3. The 0.1 ms difference between the raw and the official path is the driver.

**The WiCAN against it, 2026-11-06 (the fresh unit 44bd8d73ca79 on PCAN channel 1 beside the Openport and the simulator, which is the bus termination; the same responder, BS 15, T3 1 ms, 40 blocks; "1.5 writes" = driver 1.6 with `WICAN_J2534_WRITE_WAIT=1`, every write waiting for the device's ACK as 1.5 did; "new fw" = the event-driven, batching RX pump of 2026-11-06):** the block-end ACK latency the ECU sees, median / p95 in ms:

| path | old fw, 1.5 writes | old fw, 1.6 | new fw, 1.6 | new fw, 1.5 writes |
|---|---|---|---|---|
| USB CDC serial | 2.4 / 3.1 | 2.3 / 3.3 | **1.3 / 1.5** | 1.3 / 1.6 |
| USB-NCM 192.168.82.1 | 4.2 / 5.3 | 4.3 / 5.2 | **3.4 / 3.8** | 3.4 / 3.7 |
| WiFi, the PC on the WiCAN's own hotspot (ping 1.2 ms) | 5.2 / 8.0 | 5.5 / 9.5 | **4.3 to 4.8 / 7.6 to 13.1** (4.6 / 8.2 over 240 blocks) | 4.3 / 7.9 |
| WiFi through the Pi tunnel (the bench's control path, not a user path) | 46.1 / 68.3 | 48.2 / 67.1 | 49.0 / 68.1 | - |
| Tactrix Openport 2.0, official driver | 1.4 / 1.6 | | | |

So in the READ direction (the ECU sends, the tool acknowledges) the firmware pump is the lever: USB CDC lands on the Openport's number (2 MB projected 8.0 min against the Openport's 8.3 on its own run), NCM 9.0 min, the hotspot 9.4 to 10.2 min; the driver's write change does not move this number (the ECU-seen latency is the receive leg plus the transmit leg; the old wait only held the tool's thread), and the tunnel's 46 to 49 ms is the Pi hop (twice the 2026-10-27 figure: a different access point for the fresh unit; it is not what a user sees). In the WRITE direction (the tool sends the blocks: `--write-direction` / `--receiver`, the flash itself) the driver is the lever, since every frame the tool writes cost a round trip: a 2 MB write projected over the hotspot = 18.8 min with 1.5's wait, 11.2 min with queue-and-return alone (one request per frame, about 2 ms of device time each), **3.1 min** with the 1 ms join window (15 frames per request; the driver log shows `write request: channel 1, 15 message(s) in one request`); through the tunnel 135.5 / 23.5 / 20.4 min. The read direction over the hotspot with the join build: 4.3 / 7.6 ms, unchanged. A tool that asks for 16 messages per read with a 20 ms Timeout pays 14.3 ms per ACK on the WiCAN over CDC (13.3 min), the Openport's 15.7: the tool's own read pattern, the same on both.

One behaviour the 1.6 write exposes: a tool's response timer starts when the write is queued, not after the link's round trip, so udsoncan's 50 ms P2 (also what the simulator's 10 03 advertises) failed over the 46 ms tunnel with the default and passed with `WriteWait`, and passed with the default over the hotspot; leg D of the standard-tool bench now sets `p2_timeout` 1.0 with `use_server_timing` off (it checks the byte stream, not the link). Regression on the new firmware and driver: `j2534_std_tool_bench.py --pcan PCAN_USBBUS1` 28 checks PASS (the rig's DUT bus is PCAN channel 1 since 2026-11-06, the benches default to channel 2: `test.ps1 j2534std` fails its three PCAN-witness checks until the wiring or the default moves), `j2534_tp20_gate_bench.py --pcan PCAN_USBBUS1` TP20 RAW CAN PASS 13 checks. The third-party OPTA DLL (MCU Innovations 0.1.0, `opta_j2534_0404_tactrix.dll`) is NOT usable for the read side: its own log (`%TEMP%\j2534-0404.log`) shows every frame received and parsed, yet `PassThruReadMsgs` answers `ERR_TIMEOUT` and delivers nothing, so the raw tester was written instead. The Openport protocol as the log showed it: `ati` (identify), `ata`, `ato5 0 500000 0` (open CAN 500k, channel 5), `atf5 1 64 4` + mask + pattern (PASS filter, reply `arf5 0 0`), `att5 <n> 64` + id + data (transmit; the device echoes the frame as `ar5 ...` then confirms with `aro`), received frames `ar5` + len + kind + a 4-byte microsecond timestamp + id + data, `atc5` close, `atz` reset. Why the Openport is fast: its write call never waits for the bus, the device does its framing itself, and USB full speed gives it a round trip under 1 ms; the WiCAN pays its link's round trip (USB CDC 2.8 ms, USB-NCM 4.4 ms, WiFi tens of ms) four times per 255-byte TP 2.0 block (the request and three block-end ACKs), which is the whole difference elias saw (20 min against 40).

**The speed a TP 2.0 tool gets through the DLL** (prints `TESTER DONE` + `RESPONDER DONE` with bytes/s, the per-block time, the block-end ACK latency the ECU sees and the projected time of a 2 MB read; `TESTER FAIL` / `RESPONDER FAIL` on a lost frame or a missing ACK; ~16 s for 240 blocks; the second half of the 2026-10-27 report: "usually 20 min to flash, with wican 50"). The responder plays the ECU on PCAN: 255-byte blocks as 37 frames, `0x2N` for ordinary frames, `0x0N` at every 15th (block end: it waits for the tool's ACK `0xBN` before sending more), `0x1N` last; the tester (the DLL, 32-bit) requests blocks, answers every block end, reads one message per `PassThruReadMsgs` (`--batch 16` shows what a tool that asks for 16 pays: the DLL waited for all 16, 19 ms per ACK). Every block end is a round trip bus -> device -> DLL -> tool -> DLL -> device -> bus, and `PassThruWriteMsgs` blocks for the device's ACK (sent after the frame is on the bus): that round trip, not the bus, sets the clock. Measured 2026-10-27 (T3 1 ms, DLL 1.2): block-end ACK latency / per block / 2 MB projection = USB CDC serial 2.8 ms / 70 ms / 9.0 min, USB-NCM 4.7 ms / 76 ms / 9.8 min, WiFi station through the bench AP and the Pi 28.5 ms (p95 49, max 193) / 154 ms / 22.3 min; the real ECU's frame gap adds to all three. DLL 1.4 (`PassThruReadMsgs` on an event instead of a `Sleep(1)` poll, which costs a Windows timer tick: 15.6 ms unless an app raised the resolution, 1.3 to 1.9 ms on this PC) over USB-NCM: 4.4 ms / 56 ms / 7.7 min. 320 clean blocks over CDC after one unexplained `poweron` reboot of the DUT in the first CDC run (PSU steady at 13.5 V / 0.09 A through the reruns)
