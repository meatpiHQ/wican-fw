# The HA webhook push carries the station address

Command: `python tools\testbench\ha\ha_webhook_sta_ip_bench.py --dut <addr[:port]> (--pi rpi001 [--pi-ip 10.42.1.1] \| --serve 8199 --local-ip <own ip> \| --receiver <url>)`

Needs: main fw on DUT on a station network + a receiver host (the Pi); no vehicle needed

Moved from the `TESTING.md` test-kinds table on 2026-10-31 (the row's detail cell, whole, as paragraphs). The index row and the other stages: [../TESTING.md](../TESTING.md).

**The HA webhook push carries the station address** (→ `HA WEBHOOK STA IP PASS`, ~1 min, one planned reboot when the registration changed the stored interval; issue #977, 2026-10-11; since 2026-10-16 also the VPN state word of issue #985: `status.vpn_status` one of vpn_manager's five words and equal to `GET /api/vpn` `state`, `vpn_ip` present only while connected; `vpn_words_bench.py` runs it per state). The ha-wican integration's station IP diagnostic sensor and the device card's `configuration_url` read `status.sta_ip` from the push; the legacy `/check_status` carried that key for the polling integration, but no webhook push ever did (the legacy poster built its status with `remove_sensitive_info`, which drops `sta_ip` along with the secrets, and v6's `build_status()` never had it), so on a push-based install the sensor stayed empty for good. Reads `/api/wifi/status` (the station's address), saves `GET /api/webhook`, registers a receiver (interval 5 s, `manual_override` false so a pinned URL is honoured and put back), expects two pushes: the first (the resync) with `status.sta_ip` a dotted quad equal to the station's address, the second in `changed` mode WITHOUT it (an unchanged address is not repeated; in `full` mode every push carries it), `status:"ok"` stats, no `ha_webhooks` E line in the log ring; restore = the saved registration re-POSTed (url, urls, enabled, interval, manual_override) or DELETE when none was registered, and the stored `interval_s` back through settings PUT + submit when the registration changed it. Reaches the DUT through the usual tunnel (`ssh -N -L 18081:<dut>:80 rpi001`, `--dut localhost:18081`), the receiver on the Pi at the P4 bench AP's gateway (`--pi-ip 10.42.1.1`, `--port` free on the Pi; 8199 may be dd_receiver's); the receiver and the DUT helpers are imported from `ha_webhook_gate_bench.py`.

**2026-10-11 before the change: FAIL on exactly the three `sta_ip` checks** (`status` had 16 keys: batt_voltage, bits, ble_status, device_id, device_type, ecu_status, fw_version, hw_version, mdns, network_connected, obd_chip_status, temp_c, uptime, version, vpn_status, wifi_mode; 3 pushes in 16 s, stats ok; `test-reports/logs/issue977_20261011/sta_ip_bench_before_fix.log`).

**After the change (the same day, build `v6.00p_alfa-03-1-g3ea16c6-dirty`): the first run FAILED one check, the second push repeated every status key**, the diff mode's own wart and not the new key: a full build (the resync) never primed the prev caches, so the push after a registration went out whole once more and a real diff only started at the third (the HTTP_API says one full resync, then diffs); fixed in `ha_webhooks_payload.c` the same hour (a full build primes the caches in `changed` mode, the configured `full` mode keeps none).

**Re-run: `HA WEBHOOK STA IP PASS`** (14 checks; `status.sta_ip` 10.42.1.194 on the resync, the second push's status down to `batt_voltage, device_id, fw_version, hw_version, uptime`, 3 pushes in 13 s, 0 E lines, the interval back with one planned reboot; `sta_ip_bench_after_fix.log`, `sta_ip_bench_after_fix2.log`). The gate bench and the live stage's `ha_webhook_bench.py` check the key on their first push too (the gate bench ran on the same build right after: see its row)
