# J2534 transport probe

Command: `python3 tools/testbench/usb/j2534_transport_probe.py <dut_ip>` (ON rpi001)

Needs: main fw on DUT + rpi001 + the ECU simulator answering 7DF

Moved from the `TESTING.md` test-kinds table on 2026-10-31 (the row's detail cell, whole, as paragraphs). The index row and the other stages: [../TESTING.md](../TESTING.md).

**J2534 transport probe** (prints `J2534 TRANSPORT: raw CAN PASS or FAIL, ISO15765 bind PASS or FAIL`, ~10 s): what the PassThru server can do on THIS build, proven on the bus: a raw CAN WRITE of `7DF [02 01 00 ..]` must step the native `/api/can` tx counter and bring the ECU's `06 41 00 ..` back as RX_MSG; then CONNECT(ISO15765) without ids + a FLOW_CONTROL filter (pattern 7E8 / fc 7E0) must open an ISO-TP session and answer `10 02` with `50 02`. Since 2026-10-19 the ISO15765 data is the SAE J2534-1 layout (the 4-byte id first, both ways; `write_uds()` in `j2534_bench.py` adds it and strips it, the flow-control message carries the pad flag). Public builds carry the native `can_isotp_esp` provider since the esp_isotp commit, so both legs PASS there too (2026-10-17 on the bench at a fixed 500 kbit/s on a quiet bus: raw CAN PASS, ISO15765 bind PASS; before that provider the bind leg failed with `E j2534_server: ISO15765 not available in this build`). The same probe with `can_manager.baud = auto` on the quiet bus FAILED both legs (CONNECT fine, every WRITE `ERR_FAILED`, `tx_refused` climbing): the field report of 2026-10-17 ("J2534 driver works, communication established, no comm to the canbus"), fixed by `.\test.ps1 j2534auto`'s rule. The older `j2534_bench.py` handshake bench passes on both builds because its CONNECT(ISO15765) carries no ids and never binds. Needs `j2534_server.enabled` + `allow_lan` (from the Pi's STA side), both reboot-to-apply; restore after. Bench 2026-09-16, public build BEFORE the native provider: raw CAN PASS (tx 6 to 7), ISO15765 bind FAIL; with `can_isotp_esp` (same day): raw CAN PASS, ISO15765 bind PASS (`10 02` -> `50 02 00 32 01 F4` as ISO15765 RX_MSG). Needs `j2534_server.enabled` + `allow_lan` (reboot-to-apply; restore afterwards)
