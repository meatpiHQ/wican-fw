# OBD chip protocol store: no write on a protocol switch

Command: `.\test.ps1 attpstore` = `python tools\testbench\obd\attp_store_bench.py --dut localhost:18081 [--sim http://10.8.8.1] [--skip-refused] [--skip-bringup] [--skip-canary] [--psu auto]` (PC, the DUT through the tunnel, the console tailed beside it)

Needs: main fw on DUT + rpi001 + ECU sim v2 on the bus at 500 kbit/s + the `/ws/obd` bridge (`br_obd`, the canonical bench settings). AutoPID is switched off for the run when it is on (a planned restart each way).

The index row and the other stages: [../TESTING.md](../TESTING.md). The bench that found the mechanism, the datasheet facts and the fix design: `internal/TASK_obd_chip_protocol_store.md`; the command inventory: `internal/OBD_CHIP_COMMANDS_V6_VS_V4.md`.

## What it covers

Issue #1023, the second dead chip (an Audi Q4 e-tron on the "Audi: EV MEB" profile, beta.5). The MIC3624's memory function (`ATM1` / `ATM0`) is ON after every reset (a pin strap; nothing persists the switch), and with it on a protocol SWITCH that a request then answers on is written into the chip's non-volatile protocol store, RAM-only `ATTP` or not: the EEPROM guard's `ATSP` -> `ATTP` rewrite does not prevent it (bench 2026-11-01, `test-reports/logs/attp_flip_2026-11-01/`). The MEB profile flips the chip 6 <-> 7 seven times per poll cycle; legacy's AutoPID sent `atm0` at every start, v6 never did. The fix (components `obd_chip`, 2026-11-01): `ATM0` at the bring-up after the provisioning, and an `ATM0` transaction ahead of every protocol switch on the request path (`obd_chip_request()`: AutoPID's prelude, restore and row inits, the scans, the UDS tool, J2534, the CAN self-test), inside one transaction hold. `GET /api/obd_chip` `eeprom_guard.memory_off` counts the acknowledged ones; the bring-up's `started:` line reads `memory off`.

The store is read the only way the chip offers: `ATDPN` right after a reset (`ATZ` over `/ws/obd`) is the protocol the chip comes back on. Both protocols run at 500 kbit/s, so the DUT's CAN setting never changes; the simulator's id format (`11bit` = protocol 6, `29bit` = protocol 7) is what makes a request answer on the new protocol.

## Traps

- The refused `ATM0` leg depends on the test route's first word being the switch: an app's reset over the bridge (the store read's `ATZ`) and a row that moved the chip both make the next call send the whole prelude first, and the junk then meets `ATS1` instead of the `ATM0`. The leg makes two plain calls first and checks the second sent its word alone; a change that makes the probe invalidate the baseline would show there.
- The read-back is a reset: every `ATZ` over the bridge turns the chip's echo back on and its memory function ON. The bench sends `ATE0` after each one and leaves the chip as the bring-up left it; a run cut short leaves the echo on until the next bring-up (harmless: the request engine strips echo).
- The store is NOT among `ATPPS`'s programmable parameters and has no read word: only the protocol the chip comes back on after a reset shows it. `ATDPN` without a reset is the CURRENT protocol.
- Two store writes per run from the canary (the bench chip's store is rated for 10k cycles; the 2026-11-01 benches made about 20). `--skip-canary` for a run that must not write.
- The simulator reboots at every id format change (about 20 s). On the fixed image two flips; on an image without the fix up to six (every leg that moved the store flips back to restore it).
- An image without the fix fails the engine leg and the bring-up leg (the store reads the other protocol) and still passes the canary: that is the reproduction, not a broken bench.
- The stage leaves the DUT's CAN node with frames heard since its boot (the answered `0100` requests after the planned restart), and the node's link stays "verified" from then on: a `canselftest` run right after reads the bus LIVE "as found" with the simulator's broadcast off (2026-11-01 19:48, the one red of 61 in that run) because `can_manager_probe()` answers `live` from the sticky link flag of a running node. Restart the DUT with the bus quiet before running `canselftest` after this stage (the re-run that evening after a planned restart: PASS 61).
- The tunnel is `ssh -L 18081:<dut>:80 rpi001`; `/ws/obd` goes through the same port. The simulator is reached from the PC's own link (`lib/sim_net.py`): on this PC the LAN router is 192.168.8.1 too.
