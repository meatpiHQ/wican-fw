**A standard J2534 tool through the PassThru server** (prints `J2534 STD TOOL PASS`, ~1 min, 2 planned restarts; the second field report of 2026-10-19, "j2534 is not working (receives a timeout)": a udsoncan tester's `10 03` reached the bus as the 6-byte PDU `00 00 07 E0 10 03`, unpadded, because the device took an ISO15765 message's data as the bare UDS payload and read the pad flag from CONNECT, while SAE J2534-1 and every tool put the 4-byte CAN id first and the pad flag on each message; reproduced byte-exact and with the real DLL in `test-reports/2026-10-19_0815_j2534_std_tool_repro.md`). The device now speaks the J2534-1 layout both ways (`j2534_channel_iso.c`: one ISO-TP session per FLOW_CONTROL filter, up to 4 per channel, padding per message, single frames without a session for functional addressing, the TxDone and START_OF_MESSAGE indications). Leg C configures (j2534 on with allow_lan, autopid's groups paused; one restart). Leg U replays udsoncan 1.26.1 through the DLL byte for byte: CONNECT(ISO15765, flags 0, no ids), SET_CONFIG, CLEAR_MSG_FILTERS, the FLOW_CONTROL filter 7E0/7E8 with the pad flag in its TxFlags, CLEAR buffers, WRITE `[00 00 07 E0][10 03]` -> PCAN sees `7E0 dlc 8 [02 10 03 AA AA AA AA AA]`, the TxDone indication (rx_status 0x09, data = the id) and the reply `[00 00 07 E8][50 03 ..]`. Leg M: `22 F1 90` -> START_OF_MESSAGE (0x02, data `00 00 07 E8`) then the 17-byte VIN behind `62 F1 90`, in that order. Leg P: tx_flags 0 -> `7E0 dlc 3 [02 10 03]` on the bus and still answered, pad again -> dlc 8. Leg E: a second FLOW_CONTROL filter 7E1/7E9 on the same channel is answered from 7E9 while 7E0 still works, a 20-byte request to an id without a session is `ERR_NO_FLOW_CONTROL`, STOP_FILTER closes 7E1's session. Leg F (the filters cleared first, a flow-control session passes its id's frames as well): `[00 00 07 DF][01 00]` goes out as one frame and nothing is delivered; with a PASS filter on 7E8 the answer arrives as `[00 00 07 E8][41 00 ..]`. Leg G (since 2026-10-27): `34 ..` behind the id is forwarded (ACK NOERROR, `/api/j2534` `reflash_seen` +1; until then the reflash gate answered `ERR_NOT_SUPPORTED`), `ISO15765_ADDR_TYPE` -> `ERR_INVALID_MSG`, the id alone -> `ERR_INVALID_MSG`. Leg D: the installed `wican_j2534.dll` driven by udsoncan itself under the 32-bit Python (`j2534_udsoncan_check.py`, env `WICAN_J2534_HOST/PORT` point the DLL at the tunnel; SKIP with a note when `--py32` is absent): `10 03`, the VIN and TesterPresent answered. Leg X: settings as found (one restart), planned restarts only, no new E lines. The 32-bit Python: the embeddable `python-3.12.7-embed-win32.zip` extracted to `C:\Users\Ali\idf_tmp\py32\`, the `udsoncan` wheel unzipped into `site\` there and `site` added to `python312._pth` (udsoncan is pure Python; the DLL is 32-bit and loads only in a 32-bit process)
