# J2534 ISO 15765 flow control (ISO15765_BS, ISO15765_STMIN)

Command: `.\test.ps1 j2534fc` = `python tools\testbench\usb\j2534_flow_control_bench.py --dut localhost:18081 --j2534 localhost:18534 --pcan <the PCAN channel on the DUT's bus> [--dll <built wican_j2534.dll>]` (PC; two ssh forwards through rpi001: 18081 to the DUT's port 80, 18534 to its J2534 port 6809)

Needs: a firmware that takes `ISO15765_BS` and `ISO15765_STMIN` on the DUT + rpi001 + PCAN on the DUT's bus (`WICAN_PCAN_DUT`, the adapter's plugs may be swapped) + for leg D the 32-bit Python and a driver DLL from 1.9 (the stage passes `WICAN_J2534_DLL` when set, else `..\..\wican-j2534-driver\build\Release\wican_j2534.dll` when that file exists, and skips the leg with a note when there is none). Prints `J2534 FLOW CONTROL PASS`. About 1.5 min: two planned restarts of the unit when its J2534 server is off as found, and a wait before leg N (see the traps).

The index row and the other stages: [../TESTING.md](../TESTING.md). The standard tool's byte stream on an ISO15765 channel: [j2534std.md](j2534std.md). The layouts: section 12 of the wire protocol document in the components repository (`components/j2534_server/J2534_WIRE_PROTOCOL.md`).

## What it covers

When an ECU answers a request with more than one CAN frame, the receiver tells it how to send the rest with ISO 15765-2's flow control, `30 BS STmin`: how many consecutive frames before the next flow control (0 = all of them) and the gap between them. On a J2534 interface the two are the tool's, SAE J2534-1's `ISO15765_BS` (0x1E) and `ISO15765_STMIN` (0x1F). Until 2026-11-17 the device acknowledged a `SET_CONFIG` of them and sent BS 8 / STmin 1 ms whatever was set.

The bench plays the ECUs on the PCAN the way ISO 15765-2 writes it down: a first frame, then only the consecutive frames the last flow control allows, at the pace it asks for, and a stop when no flow control comes within a second. Every flow control the device sends is read off the bus. The ECUs take requests on 0x6F2, 0x6F3 and 0x6F4 and answer on the id + 8 (ids the bench simulator does not answer); `22 hh ll ss` is answered by 0xhhll bytes, `62 hh ll ss` and a pattern seeded by `ss`, so every byte of an answer is known. The device is driven over the wire protocol the Windows DLL speaks, and in leg D through the DLL itself.

| Leg | What is checked |

| Z | BS 0 is the rest of the message: a 4095-byte answer (585 consecutive frames, more than the 255 a block counter holds) arrives whole, every byte, and drew exactly one flow control, `30 00 00` |

## What it does not cover

- A real ECU and a real tool. The ECUs here are a model of ISO 15765-2. The contributor's flash tool on a VW engine ECU is the field case (a 64 KiB read with BS 0 / STmin 0 on his bench, on his first version of the change).
- A flash write on the unit during a transfer with a block size. By design the ECU then waits for the next flow control, so a held receive task delays the transfer instead of costing it frames, as long as a block (and the bus's other traffic in that time) fits the CAN node's 64-frame receive queue. Not run.
- The device as a sender: `BS_TX` and `STMIN_TX` are not built, it follows the ECU's flow control.
- 29-bit ids, a bus at another speed than 500 kbit/s, the USB and BLE transports (the runs went over WiFi through the tunnel).

## Traps

- **Leg N is the run with the unit's flash at rest, and the stage's own configuration restart is followed by a flash write.** A restart that changed a setting (the stage switches the J2534 server on) is followed about 25 s after boot by the configuration backup's refresh. The leg therefore waits until the unit has been up 40 s and its flash counters (`health.flash` on `/api/status`) have not moved for 3 s, and N0 fails the run when they moved during it. With the receive queue at 64 frames that write cost the run an answer (the second record); since the queue holds 256 it would not, and leg W is the run that writes the flash on purpose. If N0 fails, find what wrote (the log ring).
- `WICAN_PCAN_DUT` must name the PCAN channel on the DUT's bus in the same PowerShell command (`$env:WICAN_PCAN_DUT = 'PCAN_USBBUS2'` on this bench). On the wrong channel no ECU hears a request and every answer check fails from A3 on.
- Leg D against a driver before 1.9 fails by design (it does not send the two values), and the whole stage fails against a firmware before the change (no `GET_CONFIG` answer, `30 08 01` whatever is set). Both are what the stage is for.
- The times in leg N include the bench link (the tunnel's round trip, 46 ms on 2026-11-06): they compare the two settings on one link, they are not the bus time. The bus time of a 4095-byte answer at 500 kbit/s is about 0.15 s back to back and about 0.6 s at one frame a millisecond.
- Leg U runs after the J2534 session is closed and uses the second ECU: the UDS client keeps its session, and with it the ECU's answer id, for 5 s after a request, so leg D behind it uses the first ECU.
- The ECU model sends a frame with `time.sleep` and a busy wait for the gap, so the gaps it leaves are at least what the flow control asks; the bench does not measure the device against the gap, it reads what the device asked for.
