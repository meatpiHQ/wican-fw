**CAN listen before talk, auto bit rate and the autopid bus guard** (`tools/testbench/can/can_autobaud_bench.py` → `CAN AUTOBAUD PASS`, ~10 min, 19 DUT restarts, 3 simulator restarts; `TASK_j1939_wwh.md` phase 2). The claim: the DUT never destroys the traffic of a bus it cannot read, with its native controller or through the OBD chip, and it finds the bit rate of a live bus by listening. The JUDGE is the wire: the PCAN adapter keeps the bus alive (29-bit id 18FF1021, 200 frames/s), the ECU simulator at the same bit rate is the ACK source, and the adapter counts the bus errors it sees across every restart and in an 8 s steady window (PCAN reports a destroyed frame as one bus error plus eight counter-change messages with id 0: only the first kind counts). 19 legs: `n1`..`n4` on a 500k bus (500 normal runs; 250 normal and 250 silent read `mismatch` and destroy nothing; `auto` detects 500), `n5` the bus moves to 250k under the running auto node (demoted, re-detected), `n6`..`n8` on 250k (500 normal / silent: `mismatch`, nothing destroyed; 250 normal runs clean), `n9` auto on a silent bus stays listen-only until traffic names the bit rate, `n10` a fixed bit rate on a silent bus runs as configured, is demoted when traffic at another bit rate starts and stays listen-only after, `n11` auto + silent reads the adapter at every bit rate of the setting (125, 1000, 100, 83.3, 95.2, 33.3, 500, 250), `n12` traffic at 800k: every candidate tried, state `mismatch`, no bit rate claimed, `n13` the same bouncing node with `GET /api/can` asked from four threads for a minute: no reset (until 2026-10-05 a status read on a node the link policy was deleting loaded through a NULL register pointer, about one panic in 150 s of this: the reset of the EU truck bench's first run, TASK phase 7 addendum, finding 28); then the chip: `c0` 500k live with protocol Automatic polls, `c1` 250k live with protocol 6 pinned is parked before the first request (zero bytes to the chip, detection / std scan / test-a-PID / DTC scan / DTC clear answer 409 with the guard's sentence), `c2` Automatic with a stored protocol 6 on a 250k bus uses the chip's search and the store learns 8, `c3` silent at boot then 250k traffic: parked at the first look that reads frames, `c4` silent at boot then 800k traffic: parked as unreadable, polling resumes when it stops, `c5` (2026-11-10) 250k live with nothing standard answering (the simulator only acknowledges: a J1939 truck's bus as the chip sees it) and a detection that names a car profile pinned on protocol 6, as the Quick Setup sends it: the profile's protocol and requests stay off the bus (0 error frames while the job runs), the guard counts the refusal (`bus_guard.refused`, `refused_reason`) and a job that found nothing says why. Restores the simulator, the vehicle store's protocol and every setting; fails on an unexpected reset or an `E` line of its own tags (`/api/logs/ring`). `--only n5,c3` runs chosen legs (verdict `CAN AUTOBAUD PARTIAL PASS`). The stage opens its own ssh tunnel to the DUT (port 18081); by hand: `python tools/testbench/can/can_autobaud_bench.py localhost:8081`.

**2026-11-09 02:01: FAIL in the 250k legs, 459 s, on 6.0.0-beta.8 with the bench unit 44bd8d73ca79. Root cause, found the next morning: the OBD chip's open 500 kbit/s protocol survives the DUT's restarts since the bring-up's warm start (ATWS, components commit 2a8dbea of 2026-11-02) replaced the soft ATZ, and a chip holding a 500k protocol on a 250k bus destroys every frame: the 2026-10-03 signature again. Not the bench, not the simulator, not the native controller.** `c0` and `n1` to `n4` PASS (598 of 598 and 1600 of 1600 frames on the bus at 500k, 0 error frames), the restores PASS. From `n5` on (the running 500k auto node under a bus that moves to 250k) the adapter counts hundreds of error frames and bounces through bus-off: `n5_demotion_cost` 222 against the limit 16, `n5_wire_steady` 3832 error frames per 8 s window, and every later 250k leg inherits the storm (`n6` to `n10` wire checks, `n8_receives` rx +0, `n11_reads_125k` / `_250k`). The DUT's console (`test-reports/logs/2026-11-09_0201_autobaud/console_can_autobaud.log`) shows the native node re-detecting 250k and 60 ms later `receive error storm at 250 kbit/s (8 errors so far): the controller's interrupts are masked until the node is restarted`: the native node is a victim (399 of its 407 counted errors are of the unclassified kind, it transmits nothing), not the destroyer. The same console says `obd_chip: chip awake; warm start (ATWS) instead of hardware reset` at each of its 19 boots where the 2026-10-17 pass said `soft ATZ instead of hardware reset`. `c0` opens the chip's 500k protocol (148 polls); ATZ closed it at the next DUT restart, ATWS does not (the chip still answers `ATDP` with `AUTO, ISO 15765-4 (CAN 11/500)` after the restarts), so the chip's controller stays a 500k node in normal mode on the 250k bus. The hand matrix of that night (the id `0x18DAF1FE` clean, `auto_reset=False` clean) was ordering noise: the chip's state changed between the variants. The 2026-10-28 PASS ran beta.5, already on IDF 6.1, five days before the ATWS commit.
