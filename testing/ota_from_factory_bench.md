# A unit on the factory firmware updated to v6 the way a user does it: the v6 image through the legacy web UI's firmware page, and the way...

Command: `python tools/testbench/system/ota_from_factory_bench.py --image <v6.bin> --legacy-dir <the v4.51p release zip, extracted> [--backup auto\|<ip>\|none] [--downgrade] [--skip-flash --ssid WiCAN_<id>] [--downgrade-only --ssid WiCAN_<id>]`

Needs: DUT console + PSU + rpi001 (wtest1 / wint0 on the DUT's AP)

Moved from the `TESTING.md` test-kinds table on 2026-10-31 (the row's detail cell, whole, as paragraphs). The index row and the other stages: [../TESTING.md](../TESTING.md).

**A unit on the factory firmware updated to v6 the way a user does it: the v6 image through the legacy web UI's firmware page, and the way back** (prints `OTA FROM FACTORY PASS`, 16 checks, 23 with `--downgrade`, ~11 min; 2026-10-10, after a user on v4.51p updated to v6.00p_alfa-02 and wrote "I can not save changes via setup or manually ... Factory reset also fails"). An OTA rewrites an app partition only: the partition table in flash stays the factory one (nvs, otadata, phy_init, ota_0, ota_1 at v6's offsets, then ONE 6 MB `storage` at 0x9EE000), which has no `settings` partition, so v6's settings FS cannot mount: `E esp_littlefs: partition "settings" could not be found`, `E settings_manager: littlefs mount failed: ESP_ERR_NOT_FOUND`, `E main: settings_manager_init failed: ESP_ERR_NOT_FOUND (continuing degraded)`, then 41 x `open /settings/cfg/<c>.tmp failed` + `'<c>' persist failed: ESP_FAIL`, `FAULT boot_errors: 86 error lines at boot` (the user's count); a settings PUT answers 400 `change could not be saved`, the factory reset 500 `wipe failed` with nothing on the console (`sm_storage_wipe` on an unmounted FS). Different from the row above: there the FILESYSTEM was the legacy one under v6's own table (the 2026-10-06 probe formats it); here the TABLE is the legacy one and the probe never runs. The bench erases the DUT, writes the v4.51p release set (bootloader, table, ota data, app: the GitHub release zip), cold-boots it with the console (the version line and the AP name are readable; the legacy firmware moves UART0 to 4 Mbaud about 5 s after boot, so nothing later is, and the first v6 boot is captured from a PSU cold boot with a fresh console), rpi001 joins `WiCAN_<id>` / @meatpi# (wtest1 first, wint0 as the fallback: wint0 answered "Secrets were required" to every scripted join) and POSTs the v6 image to the legacy `/upload/ota.bin` (303; up to three tries, the USB radio lost one 3.6 MB upload in five and took 417 s for another; the device back on its AP with the image's `fw_version` is the judge), then the v6 boot from power-on (running from ota_1, 0 E lines, the settings FS mounted, no fault), the user's first save (`ap_password`, a flat key) and the factory reset through the AP. `--downgrade`: the user goes back: a legacy setting marked before the update (`sleep_volt` 12.9 through `/store_config`; the legacy reboots on it, so the first upload try can fail), the legacy app POSTed to v6's `/api/ota/upload` (`firmware=`, `{"ok":true,"received":3570592,"partition":"ota_0","reboot":true}` in 29 to 44 s), PSU cold boot: `Running firmware version: v4.51p`, `LittleFS filesystem mounted successfully`, `Partition size: total: 6291456` (= the legacy table; 6029312 would be v6's), `/load_config` on the factory AP with the mark still there.

**2026-10-10 with the fix (component `partition_migrate`, the row below): PASS on every v6 check** (`ota_from_factory_20261010_0346`: the restart history after the upload holds the `partition_migrate` record, the cold boot from power-on 0 E lines and no fault, the save 200 and persisted, the factory reset 200 + `41 settings file(s) deleted` + a reboot, the boot after it clean; the way back boots v4.51p under v6's table with its DEFAULTS: the migration formatted the legacy filesystem, config.json with it, so a user who goes back after the update starts fresh, by design).

**The rescue path `--via` (`ota_from_factory_20261010_0359`, 10 min): PASS**: alfa-02 through the legacy page (the stuck state), then the fixed image through v6's own `/api/ota/upload` (200, 32 s, into ota_0), the first boot migrated, 0 E lines, the save and the factory reset work; it showed the `boot_errors` fault the stuck boots had latched still on the Status page afterwards (count 1), which a user reads as a failed update: since that run the boot after a migration drops that one code (`dev_status_manager_fault_clear`, `v6_no_latched_faults` in the bench). Re-run with that change (`_0419`): `OTA FROM FACTORY PASS`, 24 checks, `/api/faults` empty after the rescue.

**Before the fix: FAIL on exactly the six v6 checks** (87 E lines, 41 persist failures, `boot_errors: 86`, 400, 500) on three runs (`test-reports/logs/ota_from_factory_20261010_0204`, `_0227`, `_0248`; also the cold boot by hand in `ota_v451p_to_alfa02_20261010/v6_cold_boot.console.log`); **the downgrade stage PASSED both times, the mark kept**: the rescue for a stuck user today is to upload v4.51p through the v6 firmware page, the old settings come back.
